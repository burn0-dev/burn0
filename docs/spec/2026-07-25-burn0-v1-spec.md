# burn0 v1 — Product Spec

**Date:** 2026-07-25
**Status:** Draft — in progress, one section at a time
**Relationship to prior docs:** Extends `docs/superpowers/specs/2026-07-13-burn0-design.md` (the build spec for what now exists). Where the two disagree, this document wins and says so explicitly.

---

## 0. Product statement

burn0 is a **local-first CLI observability tool for LLM *and* API usage**.

The reference point is LangSmith, moved into the terminal and widened: LangSmith shows you LLM runs; burn0 shows you LLM runs **and** every other outbound API call your app makes, with usage and cost attached to both. No cloud, no proxy, no signup — one import, data stays in SQLite on the developer's machine.

The differentiator is the second half. LLM cost tracking is a solved problem with off-the-shelf pricing data. **API usage and cost is not solved and has no ready-made data source** — that is the moat and the hard part.

### What changed vs the 2026-07-13 design

| 2026-07-13 said | v1 says |
|---|---|
| §6: "general entities display call volume + error rate + latency, **never cost**" | Reversed. API entities get usage units and cost. See §4/§5/§6. |
| §12 deferred: "per-request pricing for non-LLM APIs" | No longer deferred. It is the core differentiator. |
| No trace/session concept | Sessions and traces become first-class. See §2. |

## 1. Projects & scoping

**Status: built 2026-07-26.** P1–P4 are all closed. §§1.1–1.2 below describe the
state this section was written against and are kept because the problems explain
the design; §1.5a records what shipped and where it departed from the plan.

### 1.1 What existed before (2026-07-25)

Project identity is resolved once at capture-init and stamped on every row.

[`core/src/project/index.ts:4`](../../packages/core/src/project/index.ts) — `resolveProject(cwd, override)` resolution order:

1. explicit `project` config / `BURN0_PROJECT` env
2. nearest `package.json` walking up → its `name` field
3. that directory's basename if `name` is missing
4. git root basename
5. cwd basename

It also records `gitRoot` separately. [`core/src/storage/db.ts:33`](../../packages/core/src/storage/db.ts) `ensureProject()` upserts into `projects` and returns the id, which [`insertRows`](../../packages/core/src/storage/db.ts) writes onto every request.

Storage location — [`core/src/config/index.ts:61`](../../packages/core/src/config/index.ts):

```ts
dbPath: env.BURN0_DB_PATH ?? join(homedir(), '.burn0', 'burn0.db')
```

**One global SQLite file for every project on the machine.**

### 1.2 Problems

**P1 — Two different repos with the same package name silently merge.**

Schema declares `name TEXT UNIQUE NOT NULL` ([`storage/schema.ts:4`](../../packages/core/src/storage/schema.ts)), and `ensureProject` does `INSERT … ON CONFLICT(name) DO NOTHING` then re-selects by name. Two unrelated repos whose `package.json` both say `"name": "server"` resolve to the **same `project_id`**. Their requests become indistinguishable, and the second repo's `root_path` is silently discarded. Generic names (`api`, `server`, `backend`, `app`, `web`) make this likely, not theoretical.

**P2 — Nothing ever filters by project.**

Every read in [`core/src/query/index.ts`](../../packages/core/src/query/index.ts) is machine-global:

| Query | Actual WHERE clause |
|---|---|
| `overview` | `started_at >= ?` |
| `entityList` | `started_at >= ?` |
| `entityDetail` | `entity = ? AND started_at >= ?` |
| `traces` | `entity_class = 'llm'` (+ optional `id <` cursor) |
| `liveTail` | `r.id > ?` |
| `todaySummary` | `started_at >= ?` |
| `dbStats` | *(none)* |

The `JOIN projects` at `query/index.ts:17` exists solely to render `p.name` as a display column. Running `burn0` inside project A shows A, B and C interleaved. `burn0 export` ([`cli/src/commands/export.ts:11`](../../packages/cli/src/commands/export.ts)) dumps the entire table — every project, all time, no filter.

**P3 — `dbPath` cannot be set from the config file.**

It reads only from `env.BURN0_DB_PATH`. `runInit`'s `DEFAULT_CONFIG` ([`cli/src/commands/init.ts:4`](../../packages/cli/src/commands/init.ts)) does not include the key. A team cannot commit a repo-local burn0 database location.

**P4 — Retention is global and triggered by readers.**

[`cli/src/db.ts:6`](../../packages/cli/src/db.ts) runs `pruneRetention` + `maybeVacuum` on every read command, using **the config resolved from the CLI's cwd**. Consequences: opening the dashboard deletes data; and project A's retention settings can prune project B's rows, because the delete is `WHERE started_at < ?` with no project predicate ([`storage/retention.ts:7`](../../packages/core/src/storage/retention.ts)).

### 1.3 Terminology

Fixed for the rest of this document — these are three different things and were being conflated:

- **Project** — a codebase. Long-lived, stable across runs. This section.
- **Run** — one process lifetime of an instrumented app. Not yet modelled.
- **Session / trace** — one logical unit of work inside a run (an HTTP request, an agent invocation, a job). Spec §2.

"Show me this session's usage" is §2 work. This section only makes *project* correct.

### 1.4 Decisions (settled 2026-07-25)

| # | Decision | Chosen |
|---|---|---|
| **D1** | Storage layout | **One global DB + project filter.** `~/.burn0/burn0.db` stays; every read gains a scope. |
| **D2** | Default scope | **Current project only.** `--all` widens. Unknown cwd falls back to all rather than an empty screen. |
| **D3** | Monorepo granularity | **Git root = one project per repo.** The package becomes a sub-dimension. |

D3 has a consequence that D3's alternative did not: per-package breakdown inside a monorepo now needs somewhere to live. Tags are the obvious home and the wrong one — they are stored as opaque JSON and are not queryable (§9). So the package becomes a **first-class `service` column** instead. This keeps `packages/api` vs `packages/worker` a `GROUP BY`, not a JSON scan, and does not block on §9.

### 1.5 Design

**Two-level identity: project = repo, service = package.**

```
project   ← git root            identity, scoping unit, what `burn0` filters on
service   ← nearest package.json  sub-dimension, group-by within a project
```

`resolveProject(cwd, override)` becomes:

1. explicit `project` config / `BURN0_PROJECT` env → name override; root still resolved below
2. git root (walk up for `.git`) → **project root**; name = `package.json` `name` at that root if present, else basename
3. no git root → nearest `package.json` directory; name = its `name` field
4. no package.json → cwd; name = basename

`resolveService(cwd, projectRoot)` — new, small:

- nearest `package.json` name walking up from cwd
- `null` when it resolves to the same directory as the project root (single-package repo — no sub-dimension to show)

`BURN0_SERVICE` env overrides, for processes that don't run from their package directory.

**Identity keyed on an explicit `key`, never on the display name** (fixes P1).

The current schema made a user-editable label (`package.json` `name`) the `UNIQUE` constraint. Names are chosen by humans: they collide, change, and go missing. Identity moves to a `key` column whose value depends on where the identity came from:

```ts
key = override ? `name:${override}` : `path:${stableRoot(gitRoot ?? pkgDir ?? cwd)}`
```

Path-keyed is the default and cannot collide. Name-keyed is opt-in and *deliberately* merges: setting `BURN0_PROJECT=checkout` in three separate repos is a statement of intent that they are one project. Keying on path alone would lose that; keying on name alone is the current bug. Keying on the source of the identity gets both.

```sql
-- schema v2
CREATE TABLE projects (
  id INTEGER PRIMARY KEY,
  key       TEXT UNIQUE NOT NULL,  -- 'path:/Users/srn/code/alif' | 'name:checkout'
  name      TEXT NOT NULL,         -- display label, collisions allowed
  root_path TEXT,                  -- NULL for name-keyed (logical, not on disk)
  git_root  TEXT,                  -- NULL = resolved by fallback, not git
  first_seen INTEGER
);

-- requests gains one column
ALTER TABLE requests ADD COLUMN service TEXT;   -- NULL = single-package repo
```

```ts
export function ensureProject(db: StorageDriver, p: ProjectIdentity): number {
  const row = db.prepare(`
    INSERT INTO projects (key, name, root_path, git_root, first_seen)
    VALUES (?, ?, ?, ?, ?)
    ON CONFLICT(key) DO UPDATE SET name = excluded.name
    RETURNING id`
  ).get(p.key, p.name, p.rootPath, p.gitRoot, Date.now())
  return row.id as number
}
```

Three deliberate details:

- **`DO UPDATE`, not `DO NOTHING`** — a renamed `package.json` should update the label. Existing rows follow automatically because they hold `project_id`, not the name. With `DO NOTHING` + select-by-name, a rename silently forks the project's history into a second row.
- **`SET name` only, never `root_path`** — two repos sharing `name:checkout` would otherwise flip-flop `root_path` on every process start. It is written once at insert; NULL for name-keyed projects.
- **`RETURNING id`** collapses insert-then-select into one statement. [`driver.ts:5`](../../packages/core/src/storage/driver.ts) already exposes `.get()` on `PreparedStmt`, so this works through the adapter unchanged.

**Path normalization is required before a path becomes an identity:**

```ts
function stableRoot(dir: string): string {
  try { return realpathSync.native(dir) } catch { return resolve(dir) }
}
```

Without it, a symlinked checkout splits one repo into two projects. The `catch` is not optional — `realpathSync` throws on a deleted directory, and nothing in capture-init may throw.

No new index initially. `(project_id, started_at)` at [`schema.ts:22`](../../packages/core/src/storage/schema.ts) already covers scoping; a service filter narrows within an already-narrow set. Add `(project_id, service, started_at)` only if profiling says so — noted rather than assumed.

**Display-name collisions become cosmetic.** Group by name; for any group larger than one, append the parent directory basename. Solo projects render bare.

```
server (alif)      ~/Documents/code/alif
server (beonai)    ~/Documents/code/beonai
burn0-monorepo     ~/Documents/code/burn0-repo/burn0-1
checkout           (logical — 2 repos)
```

Schema bump is free right now — per 2026-07-13 §Q10 a version mismatch renames the DB to `.bak` and starts fresh. At v0.0.1 with only local dev data that is acceptable. It will not be after release.

**Every read takes a scope.** One shared type in `core/query`:

```ts
export interface Scope {
  projectIds: number[] | null   // null = all projects
  services: string[] | null     // null = all services within scope
  windowDays: number            // 0 = today
}
```

Threaded through `overview`, `entityList`, `entityDetail`, `traces`, `liveTail`, `todaySummary`, `dbStats`, and `export`.

**Retention becomes project-aware and stops being a read side effect.** `pruneRetention` takes a `projectId`. It runs on capture init — the writer, which knows its own project and its own config — not on dashboard open. A read command that deletes is surprising, and today it makes `burn0 export` destructive (P4).

**Config gains `dbPath`.** Resolution order: `BURN0_DB_PATH` env → `burn0.config.json` `dbPath` → `~/.burn0/burn0.db`. Relative paths resolve against the config file's directory, so a committed config stays portable across machines.

### 1.5a What shipped (2026-07-26)

Built as designed above, with four departures worth recording.

**1. `Scope` does not carry `windowDays`.** §1.5 proposed `{ projectIds, services, windowDays }`. Three of the eight readers — `traces`, `liveTail`, `dbStats` — have no time window at all, and folding one in would have forced them to accept a parameter they ignore. The time window stays a per-query argument; `Scope` is `{ projectIds, services }` and means only "what am I allowed to see".

**2. An empty array means *nothing*, not *everything*.** `{ projectIds: [] }` compiles to `0=1`. The tempting shortcut — `if (ids?.length)` — silently turns "no project matched" into "show the whole machine", which is the exact failure §1.2 P2 describes. Widening on an unresolved cwd is decided in `cli/src/scope.ts` (D2), where it is visible, and `resolveScope` reports it as `fellBack: true`.

**3. Display-name disambiguation needed a second step.** §1.5 said append the checkout directory. Two repos can share a package name *and* a directory name (`~/a/server`, `~/b/server`), so the qualified label is itself checked for uniqueness and falls through to the full path. Without the check, both rows render `server (server)` and the disambiguation silently fails to disambiguate.

**4. `burn0 init` does not write `dbPath`.** The config key exists and resolves env → file → default, with relative paths resolved against the config file's directory. It is deliberately absent from the generated `burn0.config.json`: JSON has no comments, so the only way to include it is to pin a value, and pinning `~/.burn0/burn0.db` writes a literal tilde that nothing expands. Discoverability lives in `burn0 --help` instead.

**Retention moved to the writer.** `pruneRetention` takes a `projectId` and runs from `initBurn0`. Reads no longer delete: `burn0 export` is not destructive, and one project's retention settings can no longer expire another's rows.

**`insertRows` gained a trailing `service` parameter** rather than a context object — one production caller, and a defaulted trailing argument left every test call site untouched.

### 1.6 CLI surface

```
burn0                      current project (all, if cwd resolves to no known project)
burn0 --all                every project
burn0 --project <name>     named project; ambiguous name → error listing candidates
burn0 --service <name>     narrow to one package within the project
burn0 projects             list: name, path, services, request count, last seen, size
```

Applies uniformly to `today`, `watch`, `export`, and the TUI. In the TUI the active scope shows in the header and switches with `p`; when a project has more than one distinct `service`, the Entities and traces screens gain a Service column and `s` cycles the service filter. Single-package repos never see either — no empty column, no dead keybind.

### 1.7 Open questions

- **Q1.1** Project deletion — does `burn0 projects rm <name>` exist in v1, or is deleting `~/.burn0/burn0.db` the only story? *Still open; nothing built. Retention expires rows but never removes a project row.*
- **Q1.2** — *Resolved 2026-07-26: shown, and marked.* `burn0 projects` prints `(path missing)` beside a checkout that no longer exists. Hiding it looks like data loss and auto-pruning **is** data loss; the history is real and worth keeping visible. Moving a repo still creates a second project — the old one simply reads as missing, which is an accurate description of what happened.
- **Q1.3** Repo-level rollup is now free (project *is* the repo). Does the reverse view exist — a per-service breakdown screen — or is `--service` filtering enough for v1?
- **Q1.4** Is cross-project total spend an explicit product feature (an "everything I'm burning this month" view), or just the `--all` escape hatch?
- **Q1.5** Non-JS services in one repo (a Python worker beside a Node API) have no `package.json`. Does `service` resolution need a non-npm story in v1, or is `BURN0_SERVICE` sufficient?

## 2. Runs & traces

**Status: built 2026-07-26.** Schema v3 (`runs`, `traces`, `requests.run_id/trace_id/seq`), the four-class server patch, `withTrace`, the stale sweep, `traceList`/`traceTree`, and the LLM trace list with its two-pane trace view. §2.9a records what the implementation found that the design did not anticipate.

The LangSmith-shaped core. Before this, every request was an orphan row ordered by time — no grouping of any kind existed.

### 2.0 Primary user (settled 2026-07-25)

**burn0 v1 targets long-running server backends** — Express, Fastify, Koa, Next, Hono. Not agent scripts, not CLI tools, not cron workers.

This is recorded because the rest of §2 depends on it entirely, and because it was nearly decided backwards. The trace design below was originally derived from the fact that `http.server.*` diagnostics channels work cleanly — a technology-led choice, not a user-led one. Confirming the user validates it after the fact rather than by luck.

Consequences:

- **Auto-rooting is the flagship, not a niche.** A server always has inbound requests, so traces always exist. The empty-trace-view failure mode does not occur for the target user.
- **"One inbound request" is the correct trace unit.** It is meaningless for a cron job or an agent loop; those are not the target.
- **Scripts and CLI tools degrade to run-level totals** — `run_id` is still always set (§2.2), so a script shows `run: agent.mjs — $0.42, 62 calls` with `trace_id` NULL throughout. Supported, not featured.
- **Turn inference** (grouping an LLM call with the tool/API calls that follow it, until the next LLM call) is the zero-instrumentation trace unit for scripts. Explicitly **out of v1 scope**; noted as the natural extension if the audience widens.

### 2.1 The tension

LangSmith produces a run tree because the developer instruments their code (`@traceable`, LangChain callbacks). burn0's entire promise is *one import, no code changes*. Those pull in opposite directions, and the resolution determines the whole section.

### 2.2 Two orthogonal groupings, not one

Conflating these was the mistake in earlier discussion. They are independent and both cheap:

| | **Run** | **Trace** |
|---|---|---|
| Is | one process lifetime | one logical unit of work |
| Known | always — burn0 is *in* the process | only when a root is detectable |
| Nullable | never | **yes** — NULL = outside any trace |
| Example | `node worker.mjs` from start to exit | one `POST /api/chat` |

A CLI or agent script has a run and no traces — and that is a complete, useful view (`this script run cost $0.42`). A server has one run and thousands of traces. Neither case needs the other to be meaningful.

### 2.3 Trace roots — where they come from

Priority order, first match wins:

**1. Explicit — `withTrace(name, fn)`.** Always wins. Reuses the AsyncLocalStorage already in [`context/index.ts`](../../packages/core/src/context/index.ts); `withTags` composes with it.

```ts
import { withTrace } from 'burn0'
await withTrace('nightly-summarize', async () => { /* every call inside is one trace */ })
```

**2. Inbound HTTP request — automatic, zero code.** `node:diagnostics_channel` exposes server-side request lifecycle:

```
http.server.request.start    → open trace, name = `${method} ${normalizedPath}`
http.server.response.finish  → close trace, record status
```

**Verified empirically on Node 22.12.0** — both channels fire with method and URL. This is *subscribe*, not patch: no wrapping of the app's server, consistent with the undici approach already shipped. Express, Fastify, Koa, Next and anything else on `http.Server` are covered without adapters, because the hook is below the framework.

**3. Nothing.** `trace_id` stays NULL. The request still has a `run_id`, so it is never orphaned — it appears under its run in the UI. No synthetic "everything since boot" trace, which on a long-lived server would grow without bound.

### 2.4 Structure — nested tree from day one

**Where depth actually comes from.** burn0 observes HTTP calls, not function calls, so it cannot infer nesting on its own. In v1, `parent_id` is populated by exactly one thing: a `withTrace` called inside another `withTrace`.

This must be stated plainly so expectations are right: **auto-rooted HTTP traces are always depth-1.** A developer who writes zero instrumentation gets a flat ordered list of calls under each inbound request — the tree renderer will draw a single level and nothing more. Nesting is a feature of hand-instrumented code.

**Why it is still worth building now.** Two things arrive later that produce genuinely deep trees, and both are blocked if the column is reserved rather than populated:

- **Tool calls (§8).** An agent turn is LLM → tool → the HTTP calls that tool makes. That is real depth, and it is the shape LangSmith users expect.
- **Framework detection.** LangChain, the Vercel AI SDK and the OpenAI Agents SDK all expose run hierarchies. Adopting them later means emitting spans into an existing tree, not retrofitting one.

Building the tree once, now, avoids a second schema bump and a second TUI rewrite when §8 lands.

**Query shape.** A trace subtree is fetched with a recursive CTE rather than assembled in the client:

```sql
WITH RECURSIVE subtree(id) AS (
  SELECT id FROM traces WHERE id = ?
  UNION ALL
  SELECT t.id FROM traces t JOIN subtree s ON t.parent_id = s.id
)
SELECT … FROM requests WHERE trace_id IN (SELECT id FROM subtree) ORDER BY seq;
```

**Depth is bounded.** `withTrace` refuses to nest beyond a fixed depth (proposed: 32) and flattens deeper calls onto the last valid parent. A recursive structure built from user-controlled call sites needs a hard stop, and a runaway recursion must degrade to a wrong-looking trace, never to a hung CLI or an unbounded insert loop.

### 2.4a Rendering

The TUI needs a tree renderer with expand/collapse — the most involved Ink work in the project, and net-new. Requirements: depth-prefixed first column with the numeric columns staying right-aligned across depths, collapse-by-default beyond depth 2 so a deep trace does not blow past the terminal height, and a flat toggle (`f`) that discards hierarchy for scanning.

### 2.5 Schema (v2, continues §1's bump)

```sql
CREATE TABLE runs (
  id INTEGER PRIMARY KEY,
  project_id INTEGER NOT NULL,
  service TEXT,
  started_at INTEGER NOT NULL,
  ended_at INTEGER,
  pid INTEGER,
  entry TEXT,                    -- basename(argv[1])
  node_version TEXT
);

CREATE TABLE traces (
  id INTEGER PRIMARY KEY,
  run_id     INTEGER NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  project_id INTEGER NOT NULL,   -- denormalized so scoping never needs a join
  parent_id  INTEGER REFERENCES traces(id),   -- nested withTrace only
  name TEXT,                     -- 'POST /api/chat' | explicit name
  kind TEXT NOT NULL,            -- 'http-server' | 'explicit'
  started_at INTEGER NOT NULL,
  ended_at INTEGER,
  status INTEGER,                -- inbound response status (http-server only)
  tags TEXT
);

ALTER TABLE requests ADD COLUMN run_id   INTEGER;  -- always set
ALTER TABLE requests ADD COLUMN trace_id INTEGER;  -- NULL = untraced
ALTER TABLE requests ADD COLUMN seq      INTEGER;  -- order within trace

CREATE INDEX idx_traces_project_time ON traces(project_id, started_at);
CREATE INDEX idx_requests_trace ON requests(trace_id, seq);
```

Rollups (cost, tokens, call count per trace) are **computed, not stored** — `SUM` over `idx_requests_trace` is cheap at these volumes, and a stored total would drift whenever retention prunes child rows.

### 2.6 The product payoff

This is the number the product exists to show, and nothing today can produce it:

```
POST /api/chat                      $0.0312   4 calls   2.1s
  1  OpenAI    gpt-4o           in 1,204 → out 380   $0.0142   820ms
  2  Pinecone  /query                                  —       41ms
  3  OpenAI    gpt-4o           in 2,802 → out 210    $0.0170   910ms
  4  Stripe    /v1/customers/:id                       —       120ms
```

One inbound request, its true total cost, and the LLM *and* API calls that produced it interleaved in order. LangSmith cannot show rows 2 and 4. That is the whole thesis of the product in one screen.

That view is what zero instrumentation buys — depth-1, per §2.4. A developer who adds `withTrace` gets depth:

```
POST /api/chat                        $0.0312   4 calls   2.1s
├─ retrieve-context                   $0.0004   2 calls   210ms
│  ├─ Pinecone  /query                     —              41ms
│  └─ OpenAI    text-embedding-3      $0.0004            169ms
└─ answer                             $0.0308   2 calls   1.8s
   ├─ OpenAI    gpt-4o          1,204 → 380  $0.0142     820ms
   └─ OpenAI    gpt-4o          2,802 → 210  $0.0170     910ms
```

### 2.7 Retention interaction

`traces` and `runs` prune with their requests. `ON DELETE CASCADE` handles runs → traces; requests are pruned by `started_at` independently, so a trace can outlive its children and must render as "N calls expired" rather than an empty tree. Empty runs and traces are swept in the same pass.

### 2.8 Decisions (settled 2026-07-25)

| # | Decision | Chosen |
|---|---|---|
| **D4** | Trace structure | **Nested from day one.** `parent_id` populated by nested `withTrace`; recursive-CTE reads; tree renderer in the TUI. See §2.4 for the depth-1 caveat on auto-rooted traces. |
| **D5** | Auto-rooting | **On by default.** `http.server.*` subscription is active unless `traces.http: false`. Passive subscribe — no wrapping, no added request latency. |
| **D6** | Default LLM view | **Trace-grouped by default**, `f` toggles the flat chronological list. |

D6 changes an existing, tested screen: [`screens/Traces.tsx`](../../packages/cli/src/tui/screens/Traces.tsx) currently renders a flat `query.traces()` list and is covered by `tui-traces.test.tsx`. It becomes the toggle state rather than the default, and the grouped view is net-new alongside it.

An escape hatch is required, not optional: when a project has **no traces at all** — a plain script, or `traces.http: false` — the grouped view must fall back to flat automatically rather than render an empty screen. The "(untraced)" bucket carries requests whose `trace_id` is NULL so nothing is ever invisible.

### 2.9 Implementation — how a call is attached to a trace

**Correction to §2.3.** An earlier draft of this section claimed burn0 could trace by *subscribing only, never patching*. **That was wrong**, and the correction is load-bearing.

#### Why the subscribe-only design fails

`diagnostics_channel` notifies; it never hands you the handler to wrap. So a subscriber can only use `AsyncLocalStorage.enterWith()`, which Node's own docs warn against, and which the async_hooks maintainer states plainly on [nodejs/node#41978](https://github.com/nodejs/node/issues/41978):

> *"Don't use enterWith. It's been known to be unsafe since the original creation of it… unless you really know what you are doing."* — Qard (Stephen Belanger)

Root cause in the same thread, with a matching TODO still in Node's `_http_server.js`:

> *"The HTTP parser is reused on a HTTP server socket therefore all requests on the same socket get the same asyncId."* — Flarna

Issue open since 2022, unresolved. `enterWith` writes to that shared resource.

`diagnostics_channel.bindStore()` — the API built for exactly this — was tested and **does not work here**: the `subscribe` callback fires but the bound transform never runs, because Node publishes `http.server.request.start` with plain `.publish()` rather than `runStores()`. Verified on 22.12.

#### The mechanism that is correct

Wrap the server's `request` emit in `als.run()` — the same approach OpenTelemetry uses.

```ts
function patchServerClass(proto: any, label: string) {
  const orig = proto.emit
  proto.emit = function (event: string, ...args: any[]) {
    if (event !== 'request') return orig.apply(this, [event, ...args])
    const trace = openTrace(args[0])                       // req
    return als.run(trace, () => orig.apply(this, [event, ...args]))
  }
}
```

**Four classes must be patched, not one.** `https.Server` does **not** inherit from `http.Server` — its chain is `https.Server → tls.Server → net.Server → EventEmitter`. Patching only `http.Server.prototype.emit` silently misses every HTTPS and HTTP/2 server:

| Class | Reached by patching `http.Server`? |
|---|---|
| `http.Server` | ✅ |
| `https.Server` | ❌ — separate prototype chain |
| `Http2Server` | ❌ |
| `Http2SecureServer` | ❌ |

`diagnostics_channel` also does not fire for HTTP/2 at all, so it is no fallback.

**Correction, measured 2026-07-26 on Node 22.12.0.** The table above is right about what must be patched and wrong about how to reach it:

```
http2.Http2Server        === undefined
http2.Http2SecureServer  === undefined
```

**Neither class is exported from `node:http2`.** The only way to reach the prototypes is through a throwaway instance:

```ts
const H2  = Object.getPrototypeOf(http2.createServer()).constructor
const H2S = Object.getPrototypeOf(http2.createSecureServer()).constructor
```

Also measured, and all four are load-bearing:

| Check | Result |
|---|---|
| `https.Server.prototype instanceof http.Server` | `false` |
| `Http2SecureServer.prototype instanceof Http2Server` | `false` |
| Distinct prototypes among the four | **4** |
| `'request'` observed through `Http2Server.prototype.emit` | **yes** (compat API; full event list `newListener, listening, connection, session, stream, request`) |

Each class's own chain terminates at a *different* `Server` constructor, which is why the names look deceptively similar and the inheritance checks all come back false. Creating two throwaway servers at init is the price of admission; they are never listened on and are closed immediately.

burn0 already patches `http.request`, `https.request` and `globalThis.fetch`. This is consistent with the existing capture layer, not a new category of risk.

#### Reading the trace on the way out

One line in each of the three capture paths, beside the `currentTags()` call already there:

```ts
tags  = currentTags()
trace = takeTraceStep()      // { localId, seq } — seq increments per trace
```

Read **when the call starts**, not when it completes; by response time the async context has moved on.

#### ID resolution at write time

A trace exists in memory long before it is a row, and its requests may flush before it closes. Resolved by inserting the trace row when it **opens** (with `ended_at` NULL) and updating on close:

```
flush: 1. insert newly-opened traces  → record localId → dbId
       2. update newly-closed traces
       3. insert requests with trace_id resolved from the map
       — one transaction, traces before requests
```

Nothing on the request path but `als.run` and an integer increment. No synchronous database write on inbound requests, which would put burn0's storage latency into the app's response time.

#### Verified (Node 22.12.0)

| Scenario | Calls | Misattributed |
|---|---|---|
| Sequential, 1 keep-alive socket | 36 | 0 |
| 60 concurrent over 3 keep-alive sockets | 180 | 0 |
| 10 raw-pipelined requests, single socket write | 30 | 0 |
| Work continuing after response sent | 10 | 0 |
| Express 4.22 · Koa · bare `http` | 12 each | 0 |
| HTTP · HTTPS · HTTP/2 after four-class patch | — | all covered |

#### Known risks, unverified

| Risk | Severity | Mitigation |
|---|---|---|
| ~~**SSE / streaming responses never close the trace.**~~ | ~~High~~ — **fixed 2026-07-26** | Three layers, all tested: `res.on('close')` beside `res.on('finish')` (closing twice is a no-op, and `close` is what fires on a client disconnect); a 60 s sweep that force-closes traces open longer than 10 minutes and marks them `incomplete` rather than pretending they finished; and a hard `MAX_LIVE_TRACES` cap under both. The generous 10-minute window is deliberate — a long-lived SSE connection is legitimate, and force-closing early would split one real trace into two wrong ones. |
| Another APM patching the same method (Datadog, OTel, Sentry) | Medium | patch defensively, tolerate double-wrapping |
| Next.js — custom server, standalone mode, edge runtime | Medium | needs its own test |
| Fastify | Low | sits on `http.createServer`; untested |
| Node 20 / 24 behaviour drift | Low | tested 22.12 only |
| Cluster / worker_threads | Low | each worker is its own process; likely fine |

### 2.9a What the implementation found (2026-07-26)

**1. `seq` was being consumed by calls that were never recorded.** The first end-to-end run produced `seq = [0, 2, 4]` for three calls. Three capture paths can observe one outbound call — patched `fetch`, the undici diagnostics-channel subscriber, and the `ClientRequest.prototype` fallback — and dedup rejects the duplicates at **emit** time. But `takeTraceStep()` was being called at **observe** time, so a correctly-deduped call had already burned a sequence number. Same bug for a host matched by `ignoreHosts`.

The fix is ordering, not logic: take the step only after every bail-out has passed. Worth recording because the failure mode is quiet — the trace still renders, the numbers are just wrong, and no unit test on the trace context alone can see it. It took a real server making real calls.

**2. `seq` is shared across a whole tree, not per trace.** Each `withTrace` inherits its parent's counter object rather than starting a new one. That is what lets `traceTree` order a nested trace against its siblings by when its first call happened, using one integer, with no timestamp comparison and no second sort key.

**3. The two-pane layout needs its width stated, not inherited.** The tree pane's column widths are computed from a `columns` number; if the containing `Box` is laid out against a *different* width, the detail pane silently gets whatever is left over and its contents wrap to one character per line. `<Box width={columns}>` on the container is load-bearing.

**4. `ON DELETE CASCADE` does not fire.** The schema declares it on `traces.run_id` and `tool_io.trace_id`, but better-sqlite3 leaves `PRAGMA foreign_keys` **off** by default, so retention deletes traces, `tool_io` and runs explicitly — children before parents. A cascade that silently does not cascade is worse than no cascade, because the schema reads as though it is handled.

**5. `traceList` needs one recursive CTE, not one per trace.** A single `roots(id, root)` walk maps every trace to the root of its tree; requests then join through it. Step-shape markers (`◆◇◆◇`) are assembled in JS rather than with `group_concat`, which has no portable ordering guarantee — and a shape column in the wrong order is worse than no shape column.

**Verified end to end** (`tests/trace-e2e.test.ts`): a real instrumented server, one inbound `GET /api/chat`, three outbound calls — one token-reporting completion and two plain API calls — grouped under one trace in `seq` order, with `withTrace` nesting under the auto-rooted request and a shared step counter across the subtree. That is §2.6's screen, proven rather than asserted.

### 2.10 Open questions

- **Q2.1** Queue/job handlers (BullMQ, cron) have no inbound HTTP and no generic hook — explicit `withTrace` only, or is a documented adapter recipe needed in v1?
- **Q2.2** Trace name cardinality: `POST /api/users/12345` must normalize to `POST /api/users/:id` or the trace list becomes unusable. [`normalizeEndpoint`](../../packages/core/src/entities/index.ts) already exists — reuse verbatim, or does inbound need its own rules?
- **Q2.3** Does an outbound call made *inside* another service's inbound request (service A → service B, both instrumented) link across processes? Distributed tracing is a large scope increase; presumed out for v1.
- **Q2.4** `ended_at` when a process is SIGKILLed — traces stay open forever. Sweep on next run start, or leave and render as "incomplete"?

## 3. LLM pricing feed

LLM pricing is the half of the cost problem that has an off-the-shelf answer. This section confirms the source and fixes what is wrong with how it is consumed.

### 3.1 The source

[`pricing/index.ts:13`](../../packages/core/src/pricing/index.ts) fetches LiteLLM's `model_prices_and_context_window.json` from `raw.githubusercontent.com`, caches it at `~/.burn0/pricing.json` with a 24h TTL, and falls back to a bundled snapshot.

**Measured 2026-07-25:**

| | |
|---|---|
| Size | 1.67 MB |
| Models | 2,984 |
| Providers | 124 (fireworks_ai 293, bedrock 267, openai 219, azure 219, openrouter 96, gemini 73 …) |
| With `input_cost_per_token` | 2,511 |
| With `output_cost_per_token` | 2,508 |
| With `cache_read_input_token_cost` | 710 |
| With a `mode` field | 2,975 |
| Fetch time | ~0.3s |

Modes present: `chat` 2,285 · `image_generation` 209 · `embedding` 124 · `responses` 85 · `audio_transcription` 62 · `completion` 36 · `image_edit` 31 · `realtime` 28.

Daily refresh (the existing 24h TTL) matches the cadence this data changes at. No reason to poll harder.

**Licensing must be confirmed before shipping a bundled copy.** LiteLLM is MIT, but redistributing the data file inside an npm package should be verified against the repo's terms rather than assumed. Blocking item for §3, not for the spec.

### 3.2 Problems

**P3.1 — Lookup order is backwards, and it is wrong for a provider burn0 supports today.**

[`pricing/index.ts:60`](../../packages/core/src/pricing/index.ts):

```ts
const entry = table[model] ?? table[`${provider}/${model}`]
```

Bare name is tried **first**. But the same model is priced differently per provider, and the feed carries both keys. Measured: **14 models where the bare and provider-qualified prices disagree.**

| Model | bare | qualified |
|---|---|---|
| `gemini-2.0-flash-001` | 1.5e-7 | `gemini/…` = **1e-7** |
| `gemini-3.1-flash-image` | 5e-7 | `gemini/…` = **2.5e-7** |
| `gpt-4o-mini` | 1.5e-7 | `azure/…` = 1.65e-7 |
| `command-r-plus` | 2.5e-6 | `azure/…` = 3e-6 |
| `deepseek-v4-pro` | 4.35e-7 | `fireworks_ai/…` = 1.74e-6 |

The Gemini rows are live: `generativelanguage.googleapis.com` maps to `provider: 'gemini'` in [`hosts.ts:15`](../../packages/core/src/entities/hosts.ts), so a real Gemini call today resolves the bare key and is billed at **1.5× the correct rate**. Fix is one line — try `${provider}/${model}` first, fall back to bare:

```ts
const entry = (provider && table[`${provider}/${model}`]) ?? table[model]
```

**P3.2 — The "bundled snapshot fallback" is a 5-model stub.**

`pricing/snapshot.json` is 647 bytes containing `gpt-4o`, `gpt-4o-mini`, `claude-sonnet-4-5`, `claude-haiku-4-5`, `gemini/gemini-2.0-flash`. Against 2,984 models in the feed, a developer who is offline on first run gets no pricing for 99.8% of models — and the July spec described this path as a working fallback. It is a placeholder.

(Its keys are also inconsistent — four bare, one `gemini/`-prefixed — which is the same ambiguity as P3.1 showing up in hand-written data.)

**P3.3 — The cost model is token-only; 300+ models are not priced in tokens.**

[`computeCost`](../../packages/core/src/pricing/index.ts) multiplies in/out/cached token counts. But `image_generation` (209 models) prices per image, `audio_transcription` (62) per second, `realtime` (28) per session-second. Those responses carry no `usage` block, so [`parseUsage`](../../packages/core/src/llm/parse.ts) returns null, cost stays NULL, and the spend is silently invisible. A team generating DALL·E images sees `$0.00`.

The feed already carries the discriminator — the `mode` field, present on 2,975 of 2,984 entries — and burn0 ignores it.

**P3.4 — Tiered rates are dropped.** `gpt-4o` alone carries `input_cost_per_token_batches`, `input_cost_per_token_priority`, and `cache_read_input_token_cost_priority`. burn0 reads three fields and ignores the rest, so batch-API traffic is billed at standard rates.

**P3.5 — Staleness is invisible.** Nothing surfaces when prices were last fetched. A developer running offline for a week sees costs computed from week-old data with no indication.

### 3.3 Design

**Lookup:** provider-qualified first, bare second, then unpriced. Applies to the snapshot too, which gets regenerated with consistent keys.

**Snapshot generation moves to build time.** A `scripts/fetch-snapshot.ts` run at `prepublishOnly` writes a real snapshot. Shipping all 1.67 MB inflates the package; the proposal is to filter to `mode: chat|embedding` entries from providers in [`hosts.ts`](../../packages/core/src/entities/hosts.ts) plus the top-N by usage — a few hundred KB — and let the runtime fetch cover the long tail. Exact filter is D8.

**`mode` becomes part of the cost decision.** `computeCost` dispatches on it rather than assuming tokens. v1 scope for non-token modes is D9; whatever ships, an unpriceable-but-recognized call must render as `unpriced` and never as `$0.00` — a false zero is worse than a visible gap.

**Staleness surfaces in the UI.** `fetchedAt` is already stored in the cache file. Footer shows `pricing: 3h ago`, and turns amber past 48h.

**Gateway-routed models** (self-hosted proxies whose hostname isn't in `hosts.ts`) have `provider = null`. They fall to the bare-name lookup, which is correct behaviour — and requires removing the `&& provider` gate in [`enrich.ts:38`](../../packages/core/src/capture/enrich.ts) that currently discards their cost entirely. Tracked in §6.

### 3.4 Source evaluation (2026-07-25)

Five sources fetched and compared. All free, none requiring auth.

| | LiteLLM | models.dev | Helicone | Vercel GW | OpenRouter |
|---|---|---|---|---|---|
| Distinct model IDs | **2,429** | 2,299 | 765 | 306 | 345 |
| IDs only it knows | 1,794 | 1,352 | 383 | 0 | 1 |
| Cache-read price | 710 | **2,579** | 127 | — | — |
| Cache-write price | — | **961** | — | — | — |
| Tiered pricing | partial | **254** | — | — | — |
| Ground-truth spot check | **5/5** | 4/5 | 3/3 | 2/2 | 2/2 |
| Latest model (`claude-opus-5`, rel. 2026-07-24) | **✅ day-1** | ✅ | — | — | — |

**Overlap is low: only 22% of the 4,529-ID union is known by two or more sources.** No feed is authoritative; they cover largely disjoint slices.

**Where sources disagree (5–30% pairwise), three causes, only one is a defect:**

1. *Open-weight models hosted by many providers* — `gpt-oss-120b` ranges $0.037–$0.35. Not an error: Together, Fireworks, DeepInfra and Vercel genuinely charge different rates for the same weights. **The host is the price.**
2. *Tiered pricing flattened differently* — `gemini-2.5-pro` reads $1.25 / $1.654 / $2.50 depending on source, because each picks one number for a context-tiered model.
3. *Lag on brand-new models* — `claude-fable-5` is $10 in LiteLLM, absent from models.dev.

On mainstream first-party models (`gpt-4o`, `claude-*`, `gemini-*`) **every source agrees exactly.** Source choice matters far less than lookup correctness.

### 3.5 Decisions (settled 2026-07-25)

| # | Decision | Chosen |
|---|---|---|
| **D7** | Primary source | **LiteLLM.** Widest first-party coverage, day-1 on new models (Opus 5 priced within 24h of release), all 12 `hosts.ts` providers covered, 5/5 on ground truth. 24h TTL retained; `pricingTtlHours` already configurable. |
| **D8** | Secondary | **models.dev, enrichment only** — cache-write (961 models) and tiers (254) where LiteLLM has nothing. Never used for primary lookup: its first-party entries use marketing names, not the dated API IDs SDKs send. |
| **D9** | Snapshot | Generated at build time from LiteLLM, filtered to `hosts.ts` providers. Current 647-byte / 5-model stub replaced. |

### 3.6 Resolution order (source-independent)

This matters more than which feed is chosen, and survives any future source swap:

```
1. table[`${provider}/${model}`]   ← provider-qualified wins
2. table[model]                    ← bare fallback
3. unpriced                        ← never $0.00
```

Justified by cause (1) above: for open-weight models the hosting provider determines price, and burn0 *already knows the host* from [`entities/hosts.ts`](../../packages/core/src/entities/hosts.ts). That is a structural advantage over any tool that sees only a model string, and the current bare-first order throws it away.

**Zero-priced entries are unpriced, not free.** Measured: **70 chat models in LiteLLM carry `$0.00 / $0.00`** (e.g. `deepseek-v3-2-251201`, `anthropic.claude-mythos-preview`). `computeCost` used to find the entry, multiply by zero and return `0` — not `null` — so a paid call was written to the DB as genuinely free and summed into Overview as $0.

*Fixed 2026-07-26:* an entry with neither an input nor an output rate returns `null`. Some models genuinely are free and the data cannot distinguish the two cases, so the gap is the honest answer.

**Three fixes landed together, all one or two lines and all previously mis-billing:**

| Fix | Was | Now |
|---|---|---|
| Lookup order | `table[model] ?? table[\`${provider}/${model}\`]` — bare first | provider-qualified first. Gemini was billed at **1.5×** |
| `$0/$0` entries | returned `0` | return `null` |
| `enrich.ts` cost gate | `if (model && provider)` | `if (model)` — a gateway-routed call has `provider: null` and the bare lookup is correct for it; the gate discarded its cost outright |

**And one display rule they exposed.** A real cost below `$0.00005` rendered as `$0.0000` — technically rounding, indistinguishable from free at a glance. It now renders `<$0.0001`. Same principle as null-is-not-zero, one decimal place further down.

**Tiered rates are represented, not flattened.** `gemini-2.5-pro`-style context tiers and `_batches` / `_priority` variants are carried through rather than collapsed to one number, or cost is wrong by up to 2× depending on context length.

- **Q3.2** Historical pricing: cost is computed at insert from *then-current* prices and never revisited. Correct in principle, but a price change makes old and new rows non-comparable. Store the pricing snapshot version per row?
- **Q3.3** Validate feed shape before overwriting the cache — a truncated or malformed fetch currently replaces good data with garbage.
- **Q3.4** Non-token modes (image 209, audio 62, realtime 28) — v1 or later? The `mode` field is plumbed either way; the question is whether pricing logic ships for them now. Deferring means image generation renders `unpriced`, which is honest but visibly incomplete.

## 4. API usage units

The differentiator, and the part with no off-the-shelf answer. §3 exists because someone already solved LLM pricing. Nothing equivalent exists here.

### 4.1 Why this is harder than tokens

For an LLM call, "usage" is one thing — tokens — and the provider *hands it to you* in the response body. For a non-LLM API there is no shared unit and usually no reported quantity at all:

| Service | Billed by |
|---|---|
| Twilio | SMS **segments** (160 chars each) |
| SendGrid / Resend | **emails** (recipients, not requests) |
| Stripe | **% of a monetary amount** in the payload |
| AWS S3 | **bytes** transferred + requests |
| Google Maps | **calls** |
| Supabase Pro | **nothing per call** — flat $25/mo |
| GitHub API | **free** |

Seven services, six different billing models, and none of them return a usage figure. The quantity has to be *derived* from the request burn0 already captured.

### 4.1a Scope decision (2026-07-25): usage means request count

**API usage in v1 is request counts, grouped by product.** Not payload-derived quantities. Cost is deferred to §5 and is not v1 scope.

This is a deliberate narrowing of the section drafted below, and it is the right one:

- It is **exactly how vendors report usage themselves.** Resend's own dashboard reads "Email API — 45.8k requests," not "45.8k emails." Matching the vendor's own framing means burn0's numbers can be checked against the vendor's invoice.
- It needs **no payload access**, so it works with `capturePayloads: false`, survives the 7-day payload retention window, and cannot be broken by redaction or body truncation.
- It is **exact**, not estimated. A count of captured requests is a fact.

The target shape:

```
Resend                       70.8k reqs   30d
  Email API                  45.8k
  Marketing Email API        25.0k
  Domains                       12
```

§§4.3–4.4 below describe the fuller payload-extraction model. It is retained as **design notes for §5**, not as v1 scope.

### 4.2 Grouping: real endpoints, not curated product names

**Decision (2026-07-25): show the actual API endpoints. No product-name mapping in v1.**

An earlier draft proposed mapping endpoints to vendor product names (`/emails` → "Email API"). Rejected, for a reason that outweighs the nicer labels: **an endpoint list is data; a product name is a guess about how a vendor groups its billing.** The guess can be wrong, and it goes stale silently whenever the vendor reorganizes.

Dropping it removes the two largest costs in this section:

- **The research.** Product maps for ~50 vendors means reading each one's API docs to infer their metering boundaries. That was the section's real cost, and it is not engineering work.
- **The maintenance.** A stale map degrades invisibly — an endpoint moves into a new group, silently falls back to the entity name, and stops being counted where the developer expects it.

An endpoint list has neither problem. It is complete by construction, correct by definition, and [`entityDetail`](../../packages/core/src/query/index.ts) already produces it.

```
Resend                                  70.8k reqs   30d
  POST /emails                          45.8k
  POST /audiences/:id/contacts          18.0k
  POST /broadcasts                       7.0k
  GET  /domains                            12
```

Product grouping stays available as a **later, optional** layer — added per vendor only where the endpoint list proves genuinely unreadable, driven by real need rather than by pre-filling 50 vendors on speculation.

### 4.2a Two consequences that become load-bearing

Promoting endpoints to the primary view turns two previously cosmetic details into correctness requirements.

**Method must be part of the grouping key.** `entityDetail` did `GROUP BY normalized_endpoint` with no method, so `POST /emails` (sends mail, costs money) and `GET /emails` (lists mail, does not) collapsed into a single row.

*Resolved 2026-07-26:* `usageRows` groups by `method, normalized_endpoint`. `entityDetail` was **deleted** rather than fixed — the Usage tree superseded its only caller (the old Entities screen), and leaving a known-wrong query in the exported core API is worse than removing it.

**Normalization quality now decides whether the screen is usable.** [`normalizeEndpoint`](../../packages/core/src/entities/index.ts) collapses only three segment shapes: all-numeric, UUID, and 16+-char hex. Anything else stays literal — so `/contacts/john.doe@example.com`, slug paths, short base64 ids and API-key-in-path all produce one row per distinct value. One entity can render thousands of rows instead of a dozen.

(The 2026-07-13 spec §6 claimed "base64-ish path segments → `:id`". The implementation does not do this — the claim was never true.)

Required additions, ordered by risk:

| Shape | Example | Rule |
|---|---|---|
| Email in path | `/contacts/a@b.com` | contains `@` → `:id` |
| Slug with embedded id | `/posts/my-post-a3f9c1` | trailing hex/digit run ≥6 → `:id` |
| Short base64 / nanoid | `/v1/x/aB3dEf9k` | ≥8 chars, mixed case + digits, no vowel-run → `:id` |
| Long opaque token | `/files/AKIA…` | length ≥ 24, no `.` → `:id` |

### 4.2b Show everything — no thresholds, no top-N

**Decision (2026-07-25): every entity and every endpoint is shown, at any volume.** An entity with 2 requests renders as 2 requests. No minimum count, no "top 10", no truncation of a long tail.

This follows from a property burn0 already has: **every captured request carries a hostname, so every request resolves to an entity.** [`detectEntity`](../../packages/core/src/entities/index.ts) matches [`hosts.ts`](../../packages/core/src/entities/hosts.ts) first and otherwise falls back to the registrable domain. There is no unmatched case and no gap to hide.

A consequence worth stating plainly, because it was previously misdescribed in this spec: **`hosts.ts` is a display-name table, not a coverage table.** Its 26 entries decide whether a row reads `Supabase` or `supabase.co`. A service absent from it is fully counted, grouped and shown — just under its domain. See §7.

**Render is windowed; data is not.** The existing screens already slice to terminal height ([`Traces.tsx`](../../packages/cli/src/tui/screens/Traces.tsx) computes `maxRows` from `useTermSize`), so a long list is a scrolling problem, not a data problem. Lists sort by count descending, and scrolling reaches the tail.

An earlier draft proposed collapsing endpoints past a threshold into `… N more`. **Rejected** — it hides exactly the signal that matters. If poor normalization produces four thousand endpoint rows each with a count of 1, that *is* the diagnostic: a visible flood of singletons says "this entity needs a normalization rule." Truncating it would conceal the defect and silently drop real traffic from the developer's view.

The normalization rules in §4.2a still matter — they make counts *meaningful* by grouping `/contacts/a@b.com` and `/contacts/c@d.com` into one row. They are no longer load-bearing for *readability*, because nothing is hidden either way.

### 4.2c The hierarchy: vendor → service → host → endpoint → call

Usage is a **drill-down tree**, not a flat list. Five levels:

```
AWS                                            8.0k        vendor
├─ S3                                          3.5k        service
│  ├─ s3.us-east-1.amazonaws.com               3.4k        host
│  │  ├─ GET /:bucket/:key    3.1k  in 2.1MB  out 4.8GB    endpoint
│  │  └─ PUT /:bucket/:key      300  in 1.2GB  out 4KB
│  └─ s3.eu-west-1.amazonaws.com                100
│     └─ GET /:bucket/:key      100  in 60KB  out 140MB
└─ Bedrock                                     4.5k
   └─ bedrock-runtime.us-east-1.amazonaws.com  4.5k
      └─ POST /model/:id/invoke 4.5k  in 1.2M tok  out 380k tok
```

Pressing enter on an endpoint opens the call list, and enter again opens the payload — [`DebugScreen`](../../packages/cli/src/tui/screens/Debug.tsx) already renders Input/Output panels for LLM calls; it generalizes to any request.

**Four of the five levels already exist in the data.**

| Level | Source | Status |
|---|---|---|
| Vendor | `hosts.ts` | **new field** |
| Service | `entity` | exists; AWS/Google need subdomain splits |
| Host | `hostname` | **already stored on every row, never grouped by** |
| Endpoint | `method` + `normalized_endpoint` | exists (method not yet in the key — §4.2a) |
| In/out volume | `req_bytes`/`res_bytes`, `tokens_in`/`tokens_out` | exists |
| Payload | `payloads.req_body`/`res_body` | exists |

`hostname` has been written since day one and no query has ever used it. The entire region/host level is free.

**Single-child levels auto-collapse.** Most vendors are not AWS. Forcing four keystrokes through single-item levels would be worse than today's flat list:

```
Resend                                        70.8k
├─ POST /emails                               45.8k
└─ POST /audiences/:id/contacts               18.0k
```

Vendor, service and host collapse because each has exactly one child. Branching appears only where branching exists.

**Naming is derived at read time, not stored.** Same rule as everything else in §4: group by `hostname` in SQL, then resolve vendor/service through `hosts.ts` in JS. Distinct hostnames per project number in the tens, so the fold is free — and it means **fixing or adding a host rule reclassifies all retained history**, with no schema change and no backfill. Splitting `amazonaws.com` into S3/Bedrock/SES retroactively re-buckets the last 30 days.

`provider` stays a stored column: cost is computed at insert (§3), and historical cost must not silently change when a rule is edited.

### 4.2d Two data-quality gaps this exposes — **fixed 2026-07-26**

Promoting in/out volume to a visible column surfaced two defects that were previously invisible. Both are now closed.

**Byte counts were zero on the undici path.** [`undici-dc.ts`](../../packages/core/src/capture/undici-dc.ts) emitted `reqBytes: 0, resBytes: 0` — the diagnostics_channel subscriber observes metadata only, never body chunks. As a headline column that read as "no data transferred," which is a different claim from "we didn't look."

*Resolved:* `CaptureEvent.reqBytes`/`resBytes` are now `number | null`, the DC path emits `null`, and the UI renders `—`. Body observation on the DC path was **not** added — it would mean buffering every direct-undici response, which is a real cost for an unknown, and the honest gap is cheaper and equally informative.

**Byte counts were character counts.** [`fetch-patch.ts`](../../packages/core/src/capture/fetch-patch.ts) used `text.length` and `reqBody?.length` — JS string length, not byte length. *Resolved:* `Buffer.byteLength` throughout, matching [`http-patch.ts`](../../packages/core/src/capture/http-patch.ts), which was already correct. A non-string request body (stream, `FormData`, `Blob`) is unmeasured and emits `null`, not `0`.

**The `null`-vs-`0` rule needs a companion count in SQL.** `SUM` over a column of NULLs is indistinguishable from a sum of genuine zeros, so [`usageRows`](../../packages/core/src/query/index.ts) carries `bytesInKnown` / `bytesOutKnown` / `tokenCalls` beside the sums — the same shape as the existing `pricedCalls`. A zero known-count renders a gap. This is now the standard pattern for any aggregate in burn0 whose absence is meaningful.

### 4.3 The core split: usage is objective, cost is estimated

*(Design notes for §5 — not v1 scope, see §4.1a.)*

This separation is the spine of §4 and §5, and it is what makes the section shippable.

**Usage can always be counted exactly.** burn0 has the request body, the response body, the byte counts and the endpoint. "You sent 12,431 emails and 892 SMS segments this month" is a fact, derived from real traffic, and it needs no pricing data at all.

**Cost cannot.** API pricing depends on the account's plan, month-to-date volume across *all* machines, free-tier quotas, region and negotiated rates. burn0 sees one developer's local traffic. Any cost it computes for an API is an **estimate**, and must be labelled as one.

So usage ships first and stands alone. Cost (§5) is a second layer over it. A developer who never configures pricing still gets a genuinely useful product.

### 4.4 Usage model *(§5 design notes)*

Three columns, one generic shape, no per-service schema:

```sql
ALTER TABLE requests ADD COLUMN usage_kind TEXT;  -- how it's counted
ALTER TABLE requests ADD COLUMN usage_qty  REAL;  -- how many
ALTER TABLE requests ADD COLUMN usage_unit TEXT;  -- of what
```

| `usage_kind` | Meaning | `usage_unit` examples |
|---|---|---|
| `call` | one billable request | `request` |
| `item` | count extracted from payload | `email`, `sms_segment`, `row`, `image` |
| `byte` | transfer volume | `byte` |
| `duration` | elapsed/processed time | `second` |
| `value` | a monetary amount the fee is a % of | `usd` |
| `none` | flat subscription or free | — |

**`call` is the universal baseline.** Every captured request is at least one call, so an unrecognized service still gets `usage_kind='call', usage_qty=1`. Coverage degrades to "we counted your requests," never to nothing.

### 4.5 Extraction *(§5 design notes)*

An extractor is a pure function keyed on entity + method + normalized endpoint:

```ts
(method, normalizedEndpoint, reqBody, resBody, reqBytes, resBytes) => Usage | null
```

Worked examples:

```
Twilio    POST /2010-04-01/Accounts/:id/Messages.json
          → ceil(body.Body.length / 160)         item / sms_segment

SendGrid  POST /v3/mail/send
          → Σ personalizations[].to[].length     item / email

Resend    POST /emails
          → to[].length                          item / email

Stripe    POST /v1/payment_intents
          → body.amount / 100                    value / usd

S3        GET  /:bucket/:key
          → resBytes                             byte / byte

Maps      GET  /maps/api/geocode/json
          → 1                                    call / request

GitHub    *                                      none
```

**Extraction runs at insert time, inside [`enrich()`](../../packages/core/src/capture/enrich.ts) — not lazily at read time.** Two reasons, both structural: payloads are deleted after 7 days while metadata lives 30, so a lazy read would lose usage for two-thirds of retained rows; and `capturePayloads: false` means bodies are never stored at all. `call` and `byte` kinds still work in that mode; `item` and `value` degrade to `call`. That degradation must be visible, not silent.

**Ordering constraint:** extraction must run *before* [`redactBody`](../../packages/core/src/storage/redact.ts), same as model/usage parsing does today. Redaction rewrites body content, and an extractor reading a redacted body gets wrong counts.

### 4.6 Coverage strategy *(§5 design notes)*

Fifty services cannot be hand-modelled at once, and a half-modelled service is worse than an unmodelled one — it produces confident wrong numbers.

Tiered rollout:

- **Tier 0 — everything.** `call` / 1. Free, automatic, no per-service work.
- **Tier 1 — high-volume, unambiguous extraction.** Proposed ten: Twilio, SendGrid, Resend, Postmark, Mailgun, Stripe, AWS S3, Cloudinary, Google Maps, Algolia.
- **Tier 2 — community-extendable.** Extractors are data, not code, so services can be added without a burn0 release.

### 4.7 Decisions required

- **D10** — *Resolved:* no product maps. Endpoints are the grouping. See §4.2.
- **D11** — Which normalization rules from §4.2a ship in v1? Each one that misses causes row explosion; each one that over-matches merges genuinely distinct endpoints. The email and long-opaque-token rules are low-risk; the slug rule is the aggressive one.
- **D12** — Do failed requests count toward usage? A 429 or 500 is a real request the vendor may or may not meter. Proposal: count them, but show error share alongside — [`entityDetail`](../../packages/core/src/query/index.ts) already computes `errors` per endpoint.
- **D13** — *Resolved:* no truncation, no thresholds. Everything is shown; render windows to terminal height. See §4.2b.

### 4.8 Open questions

- **Q4.1** Retries double-count: an SDK retrying 3× records 3 requests. True from burn0's view, possibly wrong against the invoice. Detectable heuristically (identical body + entity within a short window) — worth it, or note it and move on?
- **Q4.2** Where do product maps for ~50 vendors come from? Each requires reading the vendor's API docs and deciding which endpoint groups they meter separately. That is the real cost of §4, and it is research, not engineering.
- **Q4.3** Vendors reorganize their APIs. A product map is a maintenance surface that silently goes stale — an endpoint moved into a new group falls back to the entity name and quietly stops being counted under its product. Detectable by tracking the unmatched-endpoint share per entity?
- **Q4.4** Non-HTTP usage: Postgres to Supabase, Redis to Upstash. Never appears as an HTTP request, so burn0 structurally cannot see it — and those are exactly the paths those vendors bill on. Accepted v1 blind spot, or does it need calling out in the UI so the number isn't read as complete?
- **Q4.5** Should burn0 show requests-per-day trend per product, or only the window total? Trend is what makes a spike visible, and the data is already there.

## 8. Tool calls & agent steps

**Status: built 2026-07-26.** Extraction (`llm/tools.ts`), the lifecycle in `context/trace.ts`, the window rule in `query.traceTree`, and rendering in `TraceView`. §8.4a records the one place the design needed sharpening.

Verified on real captured traffic — this is the demo's `/api/agent` route, rendered from the database:

```
STEP                                            COST      TOKENS     TOOK
GET /api/agent                               $0.0084   1,844→408      8ms
  ◇ POST /declare-tool  gpt-4o               $0.0019      640→28      2ms
  🔧 search_orders                                 —           —      4ms
    ◇ POST /query                                  —           —      2ms
    ◇ GET /v1/charges/ch_771                       —           —      2ms
  ◇ POST /v1/chat/completions  gpt-4o        $0.0065   1,204→380      1ms
```

### 8.1 What burn0 sees today

An agent turn looks like this from the outside:

1. app → OpenAI: *"where is my order?"*
2. OpenAI → app: **"run `search_orders(customer:'acme')`"** ← the tool call
3. app runs that function; inside it, the function calls Pinecone, then Stripe
4. app → OpenAI: here is the tool's result
5. OpenAI → app: the final answer

burn0 records four HTTP requests in a flat row and knows nothing connects them. Worse, [`extractAnswer`](../../packages/cli/src/tui/llm-io.ts) filters Anthropic content to `type === 'text'` and reads OpenAI's `message.content` — so step 2, a **tool-call-only response, renders as empty**. The most interesting message in the exchange currently displays as nothing.

### 8.2 Two halves

**Declared calls — exact.** Names, arguments, results and errors are in payloads burn0 already stores:

```
OpenAI      choices[0].message.tool_calls[]   → {id, function:{name, arguments}}
Anthropic   content[].type === 'tool_use'     → {id, name, input}
results     next request: role:'tool' messages / tool_result blocks
```

**Attribution — inferred.** Nothing in the Pinecone request says "I belong to `search_orders`."

### 8.3 Decision (settled 2026-07-26): link them

**burn0 attributes HTTP calls to the tool that caused them.** Accepted as a heuristic because the payoff is a number nothing else produces:

```
▾ POST /api/chat                     2.1s   $0.0312
  ▾ OpenAI  gpt-4o                  820ms   $0.0142
    ▾ 🔧 search_orders               340ms   $0.0021    ← cost per invocation
        Pinecone /query               41ms
        Stripe   /v1/customers/:id   120ms
    ▾ 🔧 get_weather                  90ms        —
  ▾ OpenAI  gpt-4o                  910ms   $0.0170
```

**"`search_orders` costs $0.0021 every time it runs"** requires seeing the Pinecone and Stripe calls beneath it. LangSmith records the tool call but not its downstream API traffic, so it cannot compute this. It is the §2.6 thesis applied one level down, and it is the real depth §2's tree was built for — nesting stops being something only hand-instrumented code gets.

### 8.4 The attribution rule

A tool call is **bracketed by two events burn0 observes**: the response that declared it, and the next request carrying its result. That window is the tool's execution.

```
window = [ t(response declaring tool) , t(next request carrying its result) ]
candidates = requests in the same trace whose started_at falls inside the window
```

| Case | Behaviour | `attribution` |
|---|---|---|
| Exactly one tool declared in the turn | all candidates nest under it | `window` |
| Several tools declared (parallel calls) | candidates become siblings under the *turn*, not under any single tool | `turn` |
| No candidates | tool node with no children — it did local work | `none` |
| Wrapped in `withTrace('search_orders', …)` | exact, from AsyncLocalStorage | `exact` |
| Tool never resolved | window ends at trace end, status `unresolved` | `window` |

The last two matter. **Explicit instrumentation upgrades attribution from guess to fact** — the heuristic is the zero-code path, and `withTrace` makes it exact for anyone who cares enough to annotate. And **MCP tools are exact for free**: an MCP tool call travels over HTTP to the MCP server, so burn0 observes it directly rather than inferring it.

`attribution` is stored per node so the UI can distinguish inferred nesting from known nesting rather than presenting a guess as certainty.

### 8.4a The window is half-open (found in implementation)

§8.4 defines the window as `[t(declaring response), t(next request carrying its result)]`. Taken literally — both ends inclusive — **the closing request falls inside its own window**, so every successfully resolved tool appeared to have called the LLM back itself, and every tool's cost was inflated by the follow-up completion.

The window is half-open: `[start, end)`. The request carrying the result is the boundary that *defines* the window, not a member of it.

Two smaller decisions from the same work:

- **`attribution` is decided at declaration time, not at read time.** One tool declared in a turn → `window`; several → `turn`, because parallel tool calls have overlapping windows and nothing can honestly say which one caused a given HTTP call. Those candidates stay at the turn level as siblings. Storing the decision at declaration keeps read-time attribution to a single containment test.
- **Extraction runs at insert; attribution runs at read.** They have different lifetimes. Names, arguments and results come from payloads that expire at 7 days, so they are extracted in `enrich()` before redaction. The window itself is two timestamps — metadata, alive for 30 days — so nesting is computed at read time and keeps working after the payloads are gone.

### 8.5 Failure surfaced, not swallowed

`tool_status` is `ok` · `error` · `unresolved`. This is probably the highest-value part of §8 and the easiest to skip: **agents fail quietly.** A tool returns an error, the model apologises in prose and carries on, and the trace looks successful — every HTTP call returned 200. `unresolved` catches the other shape, where the agent gave up before sending results back.

### 8.6 Schema

Tool calls are `traces` rows. No new tree machinery — they slot into the structure §2.5 already defines, with `parent_id` pointing at the LLM call's span.

```sql
ALTER TABLE traces ADD COLUMN tool_status  TEXT;  -- ok | error | unresolved
ALTER TABLE traces ADD COLUMN attribution  TEXT;  -- exact | window | turn | none

CREATE TABLE tool_io (
  trace_id  INTEGER PRIMARY KEY REFERENCES traces(id) ON DELETE CASCADE,
  args      TEXT,
  result    TEXT,
  truncated INTEGER NOT NULL DEFAULT 0
);
```

`kind='tool'`, `name` = the tool name, both already on `traces`.

**Split retention is deliberate.** Structure lives in `traces` at 30 days; bulky arguments and results live in `tool_io` at 7, pruned alongside `payloads`. A three-week-old trace still shows *which* tools ran and whether they failed — just not what they returned. (My call, not asked — say if you'd rather they share one lifetime.)

**Extraction runs at insert**, same constraint as §4.4: payloads die at 7 days, so lazy parsing would lose tool history for two-thirds of retained traces.

### 12.1a LLM screen (settled 2026-07-26, prototyped)

### 12.1b Trace view — two-pane *(built 2026-07-26)*

Modelled on LangSmith. Tree fixed on the left, detail pane on the right following the selection; `←→` steps to the previous/next trace without leaving the view. Requires **≥110 columns**; below that it falls back to the single-pane drill-down. Ink has no layout query, so this is a manual `useTermSize` branch.

**Built 2026-07-26** — [`screens/Logs.tsx`](../../packages/cli/src/tui/screens/Logs.tsx).

- **Newest first.** Enter opens [`DebugScreen`](../../packages/cli/src/tui/screens/Debug.tsx), which already exists.
- **Follow mode** prepends new rows. **Pressing ↑ or ↓ pauses following** — `tail -f` semantics; `f` resumes and jumps back to newest. Without that rule the row under the cursor shifts as rows arrive and the list is unusable.
- **Pausing does not stop ingestion.** New rows are still fetched and still rendered while paused; the cursor index is shifted by the number prepended so the row under it does not move. Dropping rows while paused would be hiding data (§4.2b), and re-fetching the gap on resume is a second code path that can be wrong.
- **Filters:** `/` cycles all · llm · api · errors (`status >= 400` **or null** — a network failure is an error, and it has no status). Entity narrowing exists in core, not yet bound to a key.
- **Scrollback** pages 50 older rows in whenever the cursor comes within 5 of the tail, using `beforeId`.
- **Volume column** is tokens for an LLM call and response bytes otherwise, and `—` when either is unreported.

### 12.3 What this needs from core

Three gaps, all small, all in code that already exists:

| Gap | Where | Fix | Status |
|---|---|---|---|
| `traces()` hard-partitions LLM vs API | `opts.llm` was a boolean, so `entity_class = 'llm'` or `!= 'llm'`, never both | third mode: `llm: true \| false \| null` | **done** |
| Pagination unused | `traces()` accepted `beforeId` and no screen passed it | Logs pages older rows in as the cursor approaches the tail | **done** |
| No in-TUI follow | `burn0 watch` streamed live but only as a separate command | Logs polls [`liveTail`](../../packages/core/src/query/index.ts) every 400 ms | **done** |

`beforeId` and `liveTail` were both built and never wired to a screen. The Logs tab was largely assembly, not new core work.

**Two things had to change in core anyway, and both were load-bearing:**

- **One predicate builder, shared.** `traces` and `liveTail` now derive their `WHERE` from the same `filterSql(TraceFilter)`. Written separately they drift, and the drift is invisible: a followed stream would append rows the paged view had filtered out, and the screen would look merely *inconsistent* rather than broken.
- **`TraceRow` gained `hostname`, `reqBytes`, `resBytes`.** `hostname` had been stored since day one and never selected by any query. Logs shows the host per row, so it stops being free.

**`beforeId` truthiness.** The cursor check was `if (opts.beforeId)`, so a cursor of `0` meant "no cursor". No row has id 0 today, which is exactly why the bug would have survived to the day one did. Now `!= null`.

- **Q12.2** — *Resolved 2026-07-26: follow is on by default.* It matches `watch`, and the surprising-motion objection is answered by the ↑-pauses rule: the first thing a user does when they want to read a row is reach for ↑, which stops the motion.
- **Q12.3** — *Resolved 2026-07-26: structured facets only in v1.* `/` cycles `all → llm → api → errors`. Free-text search needs a text-input widget and a debounce, and no evidence yet says the facets are insufficient. Entity narrowing already exists in `TraceFilter.entity` at the core level, unbound to a key.
- **Q12.4** With five tabs, is `←→` still the right switcher, or do numbered keys come back? (They were removed once already — see `progress.md`.)
- **Q12.5** — *Resolved 2026-07-26: `←→` keeps one meaning everywhere (tabs); tree movement is `h`/`l`.* Numbered tab keys were rejected — they were added and removed once already (`progress.md`), and re-adding them to free up an arrow key trades a permanent surface change for a local one. Context-sensitive binding was rejected because a key whose meaning depends on the focused pane is the thing that made the prototype confusing. `⏎` toggles expand/collapse on a branch row and drills in on a leaf, which is unambiguous because a row is one or the other.
- **Q12.6** Sort order on the LLM list is time-descending; on route grouping it is cost-descending. That puts the *highest-volume* route near the bottom when grouped, which is right for spend and wrong for spotting a volume spike. Sort toggle, or fixed?
